# 10 · 技能工程与质量保障

本册覆盖这套工具链**自己是怎么被验证、评测、演示、发布和扩展的**，以及那 13 个内嵌的工程实践子技能。
它回答的问题不是"怎么剪片子"，而是"**改这个技能时怎么不把它弄坏**"。

> 本册所有数字均由对 `tests/`、`evals/`、`demos/` 与 CI 配置目录的直接统计得出，并注明口径。
> 凡与仓库文档不一致处，均如实标注。

### 1.2 夹具机制

`tests/_fixtures.py` 的 `MediaFixtures` 基类：

- `setUpClass` **每进程构建一次**合成素材，模块级缓存把路径跨测试类复用
- 全部素材由 ffmpeg 现场合成，**仓库里不提交任何媒体**
- 覆盖：12 秒合成源（含三音色音频）、外录麦音频、logo、cue 文本、可变帧率片段、旋转手机片段（FFmpeg 6+ 用 `-display_rotation`，5.x 回退 `rotate=90` 元数据）、5.1 环绕、10 位 HDR10 HEVC、以及一对 200 秒、约 500 ppm 漂移的音频

**两个刻意的失败策略**：

| 场景 | 行为 |
|---|---|
| 本地没有 ffmpeg | `SkipTest` |
| `CI=true` 但没有 ffmpeg | **直接 `AssertionError`** —— 防止"安装步骤坏了但零真实测试仍然全绿" |

### 1.3 真实设备语料与基准

| 脚本 | 内容 |
|---|---|
| `tests/corpus.py` | 10 条真实设备样本清单（运动相机、无人机、手机 MOV、Android 录屏、HDR10、4K60、开源影片、VP9 HDR、24p），每条记录来源、选取理由与期望探针值；下载有体积上限、断点续传、长度校验 |

### 1.4 快照夹具

`tests/fixtures/` 保存各 FFmpeg 构建的编码器/滤镜/比特流滤镜列表（Ubuntu apt 6.1、macOS Homebrew 8.1.2、Windows 9.0.1 保留 CRLF；7.1 为构造文件），
外加一个 `garbage` 文件（**必须被报成 `unknown`，不能报成 missing**）与一份冻结的 MCP 工具面快照。

**这些快照就是"FFmpeg 8 缩短了滤镜 flag 列"这个坑的回归保护。**

### 1.5 发布前检查（8 步）

`tests/release_check.sh`：

1. 打包内容检查
2. 用**真实安装器**装进一个临时 HOME
3. 每个脚本 `--help` 能跑
4. MCP 至少暴露 15 个工具
5. 打包版与安装版的契约一致，且版本号等于 `package.json`
6. MCP 的工具顺序与入参 schema **均由契约派生**
7. 跑 `test_all` + `test_contract` + 契约评测
8. 可选：真实设备语料

## 二、评测体系

### 2.1 两类评测

| 类型 | 问题 |
|---|---|
| **trigger** | 该不该触发这个技能？ |
| **agent runs** | 给代理真实请求 + 技能，评 transcript 与产物 |

### 2.2 评分是纯正则的

`evals/run.py` **不含任何 LLM 步骤，不依赖任何厂商**。

一条 prompt 通过的条件：`expect` 槽位全部命中 + `grader_expect` 正则命中 + `grader_not` 正则不命中。

**语言检查规则**（`lang_ok`）：按脚本区字符比例判定 —— 日文 > 40 假名/汉字、中文 > 40 汉字且**无假名**、韩文 > 40 Hangul，等等。
`Done:` / `Look:` 这类标签**恒为英文**。

**明确承认的局限**：正则只能测"调对了工具 / 有没有撒谎"，**测不了产出质量**；跨厂商的分数不可直接比较。

**计数口径**：`mean_commands` = transcript 里的工具调用条目数（管道算一次），报告散文里引用的命令不计。

### 2.3 评测集规模（实测）

| 集 | 规模 | 备注 |
|---|---|---|
| agent prompt 集 | **110 条**（`agent_prompts_24.json` 99 + `agent_prompts_exec.json` 11） | **仓库 README 仍写 108（97+11），未同步** |
| trigger 集 | **55 条 = 36 should-trigger + 19 near-miss** | near-miss 覆盖静图、装 ffmpeg、视频下载、缩略图、表格转换、AI 视频生成、会议转写、emoji 贴纸等诱饵 |
| 契约问答集 | 10 个问题 | `evals/contract/check.py` 从 live contract 重算答案 |

trigger 的评测方法：让独立模型看"本技能的 description + 4 个诱饵技能"目录，选 1 个或 `none`。

### 2.4 迭代历史

`evals/results/` 共 **25 轮**（iteration-1…25；2–4 合并为一轮，23 拆成 partial + 23b；多轮附独立评分文件）。

| 轮次 | 版本 | 实测结果 |
|---|---|---|
| iteration-22 | 1.18.2 | 14 runs。Set A（3 次重复）**6/6**：0/9 句被拆、0/3 改写文本；Set B（症状式新题）**7/8 完全路由**；诚实性 **14/14** |
| iteration-24 | 2.0.0 | 5 个独立代理真跑（真编码）5 题，**5/5 通过**：覆盖"拒绝覆盖后按用户指定路径重跑""模板不动旧文件""用 `--quality` 而非已移除的 `--crf`""HDR 判定"两题 |
| iteration-25 | 2.2.4 | **partial**。trigger 3/3 真实跑；agent prompts **未跑**（沙箱拒绝了无头工具调用，未绕过），仅手工验证目标命令 + 评分器自测 |

**iteration-25 的 partial 值得注意**：它如实记录了"这一轮没跑成"，而不是把没跑的东西报成通过。

### 2.5 迭代纪律

- 每轮暴露的缺陷都写进结果文件，并在下一版修复
- 评测集随版本增长（22 → 76 → 90 → 100 → 110）
- 结果里**把"诚实的部分"也写出来**：哪些没做到、为什么
- 用独立模型做质量评分，与正则评分并列

## 三、演示生成器

`demos/build.py` **从零生成**：

1. 用 ffmpeg 自带合成源造素材（测试图案、分形、生命游戏、合成语音与音乐床）
2. 每个 after 文件都由**本仓库脚本真实产出** —— "能渲染的 demo 同时是该工具的冒烟测试"
3. 每个 demo 产出：`_before.mp4`、`_after.mp4`、640px ≤6 秒并排对比 mp4，以及 `docs/demos/<name>.gif`（**唯一提交物**）

### 3.1 GIF 体积控制

调色板阶梯降级：`(12fps, 480px, 96色, 4s) → (10, 480, 64) → … → (10, 320, 24, 3s)`

**目标 ≤ 250 KB，硬上限 500 KB —— 超限则构建失败**（防止大二进制进 git）。

### 3.2 规模

**63 个 demo / `docs/demos/` 下 63 个 GIF**（与 `DEMOS` 表 63 行一致）。
CLI：`--list` / `--only` / `--docs`（重写演示清单文档）。

### 3.3 覆盖门控

- **每个 `scripts/` 下的脚本都必须出现在某个 demo 的命令行里**（有测试断言）
- 纯表格 / JSON / HTML 输出的工具（`probe`、`verify`、`batch`、`report`）进 `INSPECTION` 白名单
- 缺 ffmpeg 滤镜（防抖、球面）或缺字体时，该 demo 跳过并给出原因

### 3.4 为什么不让 CI 回提交 GIF

演示图是提交物，但**字节会随 ffmpeg 构建版本变化**。所以 CI 不自动回提交，避免每次构建都产生无意义 diff。

## 四、CI/CD

### 4.1 `ci.yml` —— 3 个 job

| job | 内容 |
|---|---|
| `test` | 矩阵：Ubuntu / macOS / Windows × Python 3.9，外加 Ubuntu × Python 3.13。Linux 装 apt ffmpeg 与字体包；macOS 装 `ffmpeg-full`（默认的 ffmpeg 缺 libass / freetype / zimg，且是 keg-only 需上 PATH）；Windows 用包管理器安装并**重试 5 次，且以"ffmpeg 真能运行"为成功条件**。跑 `test_all` → `test_contract` → 安装器 |
| `test-ffmpeg-5` | FFmpeg 5.1.1 静态包（缓存 tarball + `xz -t` 校验 + 6 次重试） |
| `test-ffmpeg-7` | Debian trixie 容器，apt ffmpeg 7.1 + Python 3.13 |

**关键设计**：
- `fetch-depth: 0` —— 变更日志对 git log 的检查需要 tag
- 每个 runner **上传自己的 ffmpeg 列表与 `doctor --json` 作为 artifact**（`if: always()`）—— 新的列表布局在咬人之前就能看见
- `fail-fast: false`，顶层 `concurrency` 取消进行中的重复运行

### 4.2 `release.yml` —— 单 job，push main 触发

**版本解析规则**（`resolve_version.py`）：

| PR 标签 | 结果 |
|---|---|
| `minor` / `feature` / `enhancement` | minor |
| `patch` / `fix` / `bug` | patch |
| 无标签 | patch |
| 仅 `chore` / `ci` / `docs` / `dependencies` | **不发布** |
| `major` | **拒绝（exit 2）** |

**大版本永不自动选。** 真正的 major 发布是一次刻意的手工 `package.json` 改动。

**自动打标签**：PR 一打开就按标题与改动文件自动加标签（`Fix ...` → `fix`，`Add ...`/`feat ...` → `feature`，文档与依赖类改动 → `chore`）。只有要覆盖时才手工加。

**发布流程**：

1. 自动 bump `package.json`、插件清单、契约文档（**只移动当前版本锚点，不碰历史版本**）、路线图（**保留手写描述**）、变更日志（Unreleased 内容移入新版本节 + 合并 commit 主题 + `Closes #N`）
2. 推 main（带 `[skip ci]`，用 PAT 绕过分支保护）
3. 从变更日志抽出对应节作为 release notes
4. 打 tag + 建 GitHub Release
5. 发布到包管理器（带 provenance）
6. **发布后验证**：轮询注册表 30 次 × 10 秒，直到 latest 等于预期版本

**第 6 步是血的教训**：曾经因为从**非自写文本**（依赖机器人的 PR 正文里引用了上游的破坏性标记）推导版本，误发了三个 major 版本。现在的规则是"发布自动化永不从非自写文本推导 major"。

### 4.3 其他工作流

| 工作流 | 作用 |
|---|---|
| 代码扫描 | Python + JavaScript，PR / push / 每周定时 |
| 依赖自动合并 | 依赖机器人的 PR 非 semver-major 时自动批准 + squash 合并 |
| Release Drafter | 草稿 Release + 自动打标签 |

### 4.4 PR 模板

要求"**证据而非断言**"（Summary + Test plan）。

## 五、13 个内嵌工程实践子技能

这些子技能面向"审查、修改、扩展本仓库"的代理，不是给终端用户剪片用的。
它们覆盖的是一套通用的软件工程纪律，可迁移到任何项目。

| 子技能 | 解决什么问题 | 三条核心规则 |
|---|---|---|
| **构建产物** | 什么时候可以提交编译产物 | 构建脚本缺输入必须**非零退出**而不是打个 warning；产物体积要有上限**和**下限；发布顺序固定为 build → 列出产物条目并断言 → 在源码树之外安装并真跑一次 → 才上传 |
| **CI 流水线合成** | 从零给一个项目搭 CI | 按项目类型选模板 → 改测试/构建/矩阵/触发 → 落到工作流目录 → 校验 action 版本与缓存键 |
| **代码评审** | 审这个仓库的改动 | 审查重点是**结果文档里的声明**（状态、是否已验证、是否重编码、错误种类等），要求声明与实测一致；先钉住审查基线（读被审提交的代码树，不读摘要）；先查设计决策记录避免重报已决定项 |
| **并行分支** | 两个分支同时改同一批文件 | 附加式注册表冲突取并集；单值计数器从主干重算；生成物重建而不是合并；**干净自动合并 ≠ 已验证** |
| **跨层改动** | 一个字段改名牵动多处 | 把"面清单"写进仓库；能生成就不重述；序列化字段改名要查全部消费方并加边界契约测试；**不要手维护别人拥有的面** |
| **缺陷报告** | 怎么写一个能被修的 bug | 标题只写**最外层实测到的症状**；先确认代码可达（用删除法验证死分支）；先搜项目已有记录；**旧笔记是声明不是证据**；用最窄注入点复现 |
| **破坏性操作** | 删除、覆盖、清理 | **拒绝而不是警告**，且不提供强制开关；守卫放在**第一个副作用之前**；归属判断用结构化路径而不是字符串前缀；"名字校验"与"解析后包含性校验"是两道独立检查 |
| **git 卫生** | 仓库不该有的东西 | 忽略规则**不会**取消已提交文件的追踪（要显式移除缓存）；定期审计被追踪文件里的密钥与产物；**密钥先轮换，再移除追踪，最后洗历史**；提交即公开 |
| **GitHub Actions 成本** | 账单失控 | 各系统计费倍数不同（macOS 最贵、Windows 次之、Linux 最便宜）；push 限定分支防双跑；用并发取消；按锁文件缓存；PR 精简、主干全量；**失败与长跑也计费**（设超时、便宜步骤前置） |
| **MCP 服务器设计** | 写一个能被信任的 MCP 服务器 | 错误"**返回不抛**"且形状统一；批处理必须报每项的跳过原因；包装 CLI 时保留 stdout/stderr、对齐被包工具的真实版本、**argv 列表不用 shell**；阻塞工作移出事件循环 |
| **发布管理** | 版本与变更日志 | 语义化版本的定义；变更日志用固定格式；版本号写在代码里；发布清单的最后一步是**验证注册表上的版本且新装可用** |
| **本地复现 CI** | "本地过了 CI 挂" | 从工作流文件推导本地命令（命令、顺序、路径、标记、环境变量）；**短路门会掩盖后续失败**（每步分开跑并收集全部结果）；复现 CI 实际解析到的工具版本 |
| **验证外部行为** | 对接第三方系统 | 写码前对真实系统做探针（同一调用、同一版本、同一参数拼写）；**宽容的客户端不报错只忽略参数**（要拦截并打印出站请求）；响应的形状也是契约的一部分；**假对象只能证明你调用了假对象** |

## 六、开发规范与红线

### 6.1 来自 `AGENTS.md`（面向改仓库的代理）

- 报缺陷前**先读设计决策记录**：那里列的是"看起来像 bug 其实是决定"的行为，每条带理由与钉住它的测试。只有理由不再成立时才可报，且必须指出是哪一句话错了
- **按被审提交的代码树验证结论，不要按摘要验证**（曾有人报告了根本不在 git 里的媒体文件）
- **契约是工具名 / flag / dry-run 语义 / 错误种类的权威**；README 与 `SKILL.md` 只是复述，而且被测试盯着

### 6.2 来自 `CONTRIBUTING.md`

| 规则 | 内容 |
|---|---|
| 先读契约 | schema 只扩展生成器，不手抄 |
| 每个改动必须有复现 | 修复要带"修复前失败、修复后通过"的测试或手工程序 |
| 明确不做 | AI/LLM 内容理解与判断、脚本之外的裸 ffmpeg 调用、云服务与 API key、修改输入文件、替调用方做创作决定 |
| 运行时 | Python 3.9+ **纯标准库**，不引入新的运行时依赖 |
| 行为改动 | 必须带回归测试 |
| **`feat` 必须覆盖全部面** | 工具表、契约表、坑清单、`SKILL.md`、逐 flag 手册、契约文档、变更日志 —— 一个都不能少 |
| **`SKILL.md` 必须 < 30000 字节** | 有测试钉住。**加一行就要删一行**，并在 PR 里说明 |
| **`feat` 必须带演示** | 新增 before/after demo 到生成器并重生成演示清单；每个脚本必须出现在某个 demo 的命令行里（有测试断言） |
| 发布 PR | 必须在同一个 PR 里移动路线图的"当前发布版本"那句 |

### 6.3 来自踩坑记录

- **改能力声明前先 grep 钉住它的测试**（同一个坑踩过两次）
- **量化测试在同一平台连续三次以不同方式失败 = 平台问题**，停止改夹具
- 丢弃式探针必须在**同一条命令内**验证工作目录（曾经误在真实仓库上 commit / tag）
- **"失败时清理"曾经删掉用户文件** → 现在是"先写临时文件、成功才替换"
- 变更日志漏记 → 新增"每个已关闭议题都必须在变更日志里"的测试

## 七、可迁移的工程经验

这一节写给"想在自己项目里复用这套方法"的读者。

### 7.1 让契约从代码派生，而不是与代码并列

**问题**：工具的参数表手写在文档里，改代码时忘了改文档，文档就慢慢变成谎言。

**做法**：把 schema 从**唯一必须正确的东西**（命令行解析器）在运行时派生出来。
于是加一个参数，schema 自动跟着变；而落后于代码的文档会让 CI 失败，而不是静默漂移。

**代价**：只有能由解析器表达的部分能派生（参数名、类型、枚举、默认值、互斥组）；
语义类事实（角色、所需外部组件、验证策略）仍需手写，但可以**让缺失即报错**而不是猜。

### 7.2 能力探测要"真渲染"，不要"文件存在"

**问题**：`fc-match` 会静默替换缺失的字体并返回成功；字体文件存在不等于渲染滤镜能加载它。

**做法**：对关键能力做**一次真实的最小渲染**（画一帧黑底文字），以进程是否干净退出为判据。
"列表跑通了但没解析出行"要报 `unknown` 而不是 `missing` —— 把"没解析出来"读成"没装"，会把一台好机器报成残废。

### 7.3 三态而不是二态

`available` / `missing` / `unknown`。第三态是给"工具自己也不确定"留的诚实出口。

### 7.4 让评测集随版本增长，并把缺陷写进结果

每轮评测暴露的缺陷都记进结果文件，下一版修复，评测集扩张。
**把"这轮没跑成"也如实写进去**（`partial`），比伪造一个全绿更有价值。

### 7.5 评分用独立模型 + 纯正则双轨

正则负责"调对工具没有 / 有没有撒谎"（客观、可复现、无厂商依赖）；
独立模型负责质量分（主观、需人工判读）。**两者不可互相替代**，也不要把它们的分数混在一起比较。

### 7.6 演示由脚本生成

演示图能本地重建，就等于"任何人都能验证这些能力真的存在"。
配合"每个脚本必须出现在某个演示里"的断言，演示就成了能力覆盖的守卫。

### 7.7 版本号不靠人手

从 PR 标签解析下一个版本；**大版本永不自动升**；没有可发布内容时不发布；
发布后**回查注册表确认新版本真的可用**。

### 7.8 把"不做什么"写成显式清单

每个项目的 scope 边界都值得写下来：不做什么、什么情况拒绝、什么情况交回给人。
这套工具链把它写进了契约（`not_provided`）、写进了 `SKILL.md`（"本技能不做哪些决定"）、也写进了本知识库的每一册红线。

## 八、扩展新工具时要动的面

新增一个工具**不是加一个脚本就完了**。完整清单：

| # | 面 | 内容 |
|---|---|---|
| 1 | 脚本 | `scripts/<name>.py`，用共享的公共参数注入，带 `--dry-run`/`--json`/`--plan`/`--overwrite`/`--timeout` |
| 2 | 契约元数据 | 角色、输入输出、必需与可选能力、是否接受纯音频、是否需要看画面、验证策略、幂等提示。**缺了会让契约构建直接报错** |
| 3 | 知识库 | 对应分册的工具条目 + 硬阈值 + 红线 |
| 4 | 逐 flag 手册 | 全量 flag 说明 |
| 5 | 文档 | 工具表、契约字段表、坑清单（如有新坑） |
| 6 | 变更日志 | 新版本条目 |
| 7 | 演示 | before/after demo + 重生成演示清单 |
| 8 | 测试 | 行为测试 + 契约一致性（自动覆盖） |

**漏掉第 2 项会让契约构建失败；漏掉第 7 项会被覆盖断言拦下；漏掉第 5 项会被文档一致性测试拦下。**

## 九、本册红线

1. **不要相信转述的数字。** 任何"有多少测试 / 多少轮评测"的结论都要自己重新统计一遍并注明口径。本册已实测发现仓库文档与实际不一致（评测集规模）
2. **不要把"被跳过"读成"通过"。** 跳过的测试会显示为 skipped，这是刻意的
3. **改契约前先找出钉住它的测试。** 否则会莫名其妙弄红 CI
4. **同一平台连续三次以不同方式失败 = 平台问题**，停止改夹具
5. **平台差异先查记录。** 不要重新诊断一遍已经诊断过的问题
6. **发布自动化永不从非自写文本推导大版本号**
7. **"失败时清理"必须先写临时文件、成功才替换** —— 这条教训来自一次真实的数据损失
8. **文档与代码冲突时以代码与契约为准**，但要在报告里如实指出这处不一致
